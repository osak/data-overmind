# AI 向けレビューコンテキスト生成 — 実装計画

最終更新: 2026-09-25

状態: 実装済み

## 目的

`ai-doc-template` から保存された `*.html.review.json` を AI が直接読む代わりに、元の HTML とレビューを突合し、指摘への対応に必要な情報だけを短い形式で出力するコマンドを `data-overmind` に追加する。

このコマンドが判定する「有効性」は、コメント内容の妥当性ではなく、保存時の対象ブロックを現在の HTML 上で安全に特定できるかどうかを指す。意味上の採否は、出力を読む AI または人間が判断する。

## 利用方法

新しいツールを既存のリポジトリ構成に合わせて `cmd/review-context` として追加する。

```sh
go run ./cmd/review-context workspace/report.html
go run ./cmd/review-context --format json workspace/report.html
```

- 入力は元の HTML ファイルだけとする。
- レビューは同じディレクトリの `<HTMLファイル名>.review.json` から自動的に読む。
- 既定出力は人間にも読め、AIへの入力にもそのまま使える簡潔な Markdown とする。
- `--format json` は他のツールが扱いやすい小さな構造化表現を出す。保存用 JSON の複製にはしない。
- 出力先を指定せず、標準出力だけに書く。入力ファイルは変更しない。

## 照合モデル

HTML からブラウザ側と同じ規則でレビュー対象を復元する。

1. 対象は `p` と `li`。
2. `p` を含む `li` は、同じ表示内容への重複コメントを避けるため除外する。
3. `li` の本文からネストした `ol` / `ul` の本文を除く。
4. `h2` / `h3` をセクション境界として扱い、見出し ID がなければ `ai-doc-template` と同じスラッグ規則で補う。
5. `data-review-id` を優先し、それ以外は `<section>::p-N` または `<section>::li-N` を生成する。
6. 重複 ID には `-2`, `-3` の連番を付ける。

各コメントは次の順で現在のブロックへ照合する。

1. 保存されたブロック ID と本文ハッシュがともに一致する: `exact`
2. 本文ハッシュが文書内で一意に一致する: `relocated`
3. 保存されたブロック ID は一致するが本文が変わっている: `changed`
4. 本文が複数箇所に一致し、一意に決められない: `ambiguous`
5. 対応候補がない: `missing`

低信頼な位置番号だけで対象を決めたり、複数候補から推測で一つを選んだりしない。元 HTML の SHA-256 とレビューに記録された SHA-256 も比較し、文書全体が保存後に変化している場合は `source: changed` と明示する。

## 出力内容

Markdown の先頭には文書名、ソース状態、コメント数と照合結果の要約を置く。各コメントには次だけを含める。

- 照合状態
- 現在の対象ブロック ID（解決できた場合）
- 所属する見出し階層
- 直前の対象ブロック（存在する場合）
- 現在の対象本文。本文が変更された場合、または対象を解決できない場合は保存時引用も含める
- 直後の対象ブロック（存在する場合）
- 人間のコメント

タイムスタンプ、コメント UUID、完全なハッシュ、保存用メタデータは、指摘対応に不要なので既定出力から除く。同じ周辺ブロックが長い場合は UTF-8 を壊さず上限までで切り詰める。

コンパクト JSON は同じ意味情報をフィールド化し、値のない周辺文脈は省略する。

## 構成

- `internal/reviewcontext`: レビュー読込、HTML解析、アンカー再現、照合、Markdown/JSONレンダリング
- `cmd/review-context`: 引数処理、標準出力、終了コード
- `internal/fileserver`: 保存用スキーマの既存実装は変更しない

HTML 解析には `golang.org/x/net/html` を使う。正規表現だけで HTML を読む実装は、属性のエスケープ、入れ子、script/style、壊れにくいテキスト抽出を扱えないため採用しない。

## エラーと終了コード

- 引数不正: 終了コード 2
- HTML またはレビューを読めない、レビュー形式が不正: 終了コード 1
- `ambiguous` / `missing` を含むこと自体は正常な解析結果なので終了コード 0
- スキーマバージョンが未対応の場合は、誤読を避けるためエラーにする

## 検証

単体テストで次を確認する。

- 明示 ID と生成 ID の再現
- `p` / `li` の個別連番、ネストしたリスト、`p` を含む `li`
- 見出し ID の生成と重複回避
- `exact`、`relocated`、`changed`、`ambiguous`、`missing` の全状態
- ソースハッシュ一致・不一致
- 前後文脈と見出し階層
- 長文の UTF-8 安全な切り詰め
- Markdown と compact JSON の安定した出力
- 不正 JSON、別スキーマ、存在しないレビューへのエラー

最後にリポジトリ全体へ `go test -race ./...` と `go vet ./...` を実行し、実際の `workspace/review-test.html` から生成した出力も目視確認する。

## 完了条件

- AI が保存用 JSON を開かず、元 HTML のパス一つからレビュー指摘と現在の文脈を取得できる。
- ソース更新後でも、安全に解決できる対象と解決できない対象を区別できる。
- ブラウザ側の対象 ID 規則と CLI 側の規則が一致する。
- 既存のレビュー保存・読込 API の挙動とファイル形式を壊さない。
